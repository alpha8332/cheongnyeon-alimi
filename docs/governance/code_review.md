# 코드 리뷰 정책

## 1. 목적

코드 리뷰는 결함을 찾는 것뿐 아니라 변경 범위, 계약, 테스트와 문서가 서로
일치하는지 확인하는 절차다. 작업 브랜치의 변경은 Pull Request를 통해
`develop`에 병합한다.

## 2. PR 작성자 책임

PR을 열기 전에 다음을 확인한다.

- 브랜치가 최신 `develop`을 기준으로 하는가?
- 하나의 Issue 또는 논리적 작업 단위만 포함하는가?
- PR 제목과 설명이 변경 목적과 범위를 설명하는가?
- 관련 테스트와 정적 검사를 실제로 실행했는가?
- 실행하지 못했거나 실패한 검증을 명시했는가?
- API, Schema, DB, 환경변수와 운영 변경 문서를 갱신했는가?
- `CHANGELOG.md`와 관련 기준 문서의 갱신 필요성을 확인했는가?
- 비밀정보, 런타임 원문과 임시 파일이 포함되지 않았는가?
- 자신의 diff를 먼저 검토했는가?

PR 설명에는 최소한 작업 개요, 주요 변경, 검증 결과와 범위 밖 항목을
포함한다. 의존 PR이나 후속 작업이 있으면 함께 연결한다.

## 3. 리뷰어 책임

리뷰어는 다음 순서로 확인한다.

1. 변경이 Issue와 PR 범위에 맞는지 확인한다.
2. 아키텍처와 영역별 책임을 위반하지 않는지 확인한다.
3. 정상 흐름, 경계값, 실패 흐름과 데이터 손실 가능성을 확인한다.
4. 테스트가 중요한 동작과 회귀 위험을 검증하는지 확인한다.
5. 코드와 API·Schema·DB·문서가 일치하는지 확인한다.
6. 보안, 개인정보, 비밀정보와 외부 데이터 이용 조건을 확인한다.
7. 운영, 롤백 또는 호환성 영향이 명시됐는지 확인한다.

스타일 선호와 병합을 막아야 하는 문제를 구분한다. 차단 의견에는 발생 가능한
결함이나 위반 규칙을 구체적으로 설명한다.

## 4. 리뷰 결과

- `Approve`: 병합을 막는 문제가 없고 필수 검증이 충족됨
- `Comment`: 질문이나 선택적 개선 의견이며 현재 병합을 막지 않음
- `Request changes`: 결함, 계약 불일치 또는 필수 기준 누락으로 수정이 필요함

작성자는 변경 요청을 코드로 수정하거나, 수정하지 않는 이유와 근거를
답변한다. 큰 변경이 추가되면 리뷰어가 다시 확인할 수 있도록 알린다.

## 5. 병합 기준

다음을 모두 만족해야 `develop`에 병합할 수 있다.

- 최소 1명의 승인
- unresolved 상태의 차단 의견 없음
- 변경 범위에 필요한 테스트와 검사 통과
- 코드와 관련 문서의 일치
- 병합 충돌 없음
- PR에 검증 결과와 알려진 제약이 기록됨

실행 가능한 테스트가 아직 없는 문서 전용 변경은 링크, 파일 존재, 포맷과
내용 일관성 검증으로 대체할 수 있다. 실행하지 않은 테스트를 통과로
표시해서는 안 된다.

병합 방식은 저장소에서 허용한 방식을 사용한다. 병합 후 작업 브랜치는
삭제하고 `develop`을 최신 상태로 갱신한다.

## 6. 영역별 추가 확인

### 데이터와 Schema

- 원문 손실, 필수값, `null`, 빈 배열과 enum 규칙
- Fixture, Seed와 Schema의 일치
- 기존 소비자와 데이터 마이그레이션 영향

### Backend와 API

- 상태 코드, 오류 응답, 인증과 권한
- 트랜잭션, 페이지네이션과 데이터 접근 경계
- API 문서와 응답 Schema의 일치

### Frontend

- 로딩, 빈 결과와 오류 상태
- 접근성, 반응형 동작과 API 실패 처리
- TypeScript 타입과 API 계약의 일치

### Collector

- Timeout, 재시도, 요청 간격과 실패 격리
- 외부 응답 변경과 선택 필드 누락 처리
- 인증키, 개인정보와 원문 저장 정책

### 배포와 운영

- 환경변수, 데이터 보존과 복구
- 기존 환경과의 호환성
- 실행 및 롤백 절차

문서 갱신 세부 기준은 [문서화 정책](documentation_policy.md)을 따른다.
