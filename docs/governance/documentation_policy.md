# 문서화 정책

## 1. 목적

이 정책은 코드와 문서가 서로 다른 상태로 남는 것을 방지하고, 계획과 실제
개발 결과를 명확히 구분하기 위한 기준이다. 모든 코드 변경을 기록하는 것이
목표가 아니라, 프로젝트를 이해하고 개발·운영·검증하는 데 필요한 정보를
지속해서 정확하게 유지하는 것이 목표다.

## 2. 적용 범위와 우선순위

이 정책은 프로젝트의 코드, 데이터 계약, API, 데이터베이스, 개발 환경, 배포,
운영 및 대회 제출 자료에 적용한다.

문서와 실제 동작이 충돌하면 코드, 실행 결과와 자동화된 계약을 우선하여
사실을 확인한다. 확인 후 같은 작업에서 문서를 수정한다. 아직 구현하거나
검증하지 않은 내용은 현재 동작으로 표현하지 않는다.

협업 규칙은 [브랜치 전략](branch_strategy.md),
[커밋 작성 규칙](commit_convention.md), [코드 리뷰 정책](code_review.md),
[역할과 책임](role_assignment.md)과 함께 적용한다.

## 3. 문서별 책임

### `docs/index.md`

문서 탐색의 시작점과 빠른 갱신 기준을 제공한다. 세부 정책을 중복해서
작성하지 않고 이 문서로 연결한다.

### `docs/development/develop_plan/`

아직 완료하지 않은 Forest를 관리한다. Forest마다 계획 문서 하나를 두고,
내부 Slice의 범위, 의존성, 구현 순서, 검증과 완료 기준을 기록한다. 담당
영역이 명확한 계획은 `data/`, `backend/`, `frontend/`, `integration/` 아래에서
관리한다. 구현 결과를 계획 문서만으로 대체하지 않는다.

### `docs/development/development_notes/`

Forest가 구현 단계에 들어가면 계획과 같은 담당 영역에 실제 구현 내용과 검증
결과를 상세 문서 하나로 기록한다. Slice는
Forest 문서 내부의 섹션과 진행 현황으로 구분한다. Slice마다 파일을 만들거나
모든 Forest를 하나의 파일에 누적하지 않는다. 예정 사항은 기록하지 않으며,
남은 작업은 대응하는 Forest 계획이나 Issue로 연결한다.

### `CHANGELOG.md`

사용자와 팀이 알아야 할 의미 있는 변경을 요약한다. 개발 중 변경은
`[Unreleased]` 아래에 기록하고 릴리스할 때 해당 버전으로 이동한다.

기록 대상:

- 완료된 Forest가 제공하는 주요 결과
- 사용자가 확인할 수 있는 주요 기능과 동작 변경
- 데이터·API·DB 등 소비자 대응이 필요한 호환성 변경
- 데이터 정확성, 보안, 운영 또는 주요 사용자 동작에 영향을 주는 버그 수정
- 배포·설치·사용 방법에 영향을 주는 변경

일반적으로 기록하지 않는 대상:

- 진행 중이거나 `draft`, `approved` 상태인 계획
- 내부 리팩터링과 변수명·파일 배치 같은 구현 세부사항
- 기존 동작을 바꾸지 않는 테스트 추가
- 오탈자, 서식과 단순 문서 정리
- 하나의 Forest 결과를 구성하는 Slice별 중간 작업

하나의 Forest 결과는 원칙적으로 1~2개의 항목으로 요약하고, Slice와 변경
파일을 CHANGELOG에 나열하지 않는다. 상세 구현, 결정과 검증 결과는 담당 영역의
개발 기록에 작성하고 CHANGELOG 항목에서 해당 기록을 링크한다. 담당자별
CHANGELOG는 만들지 않고 루트 파일 하나를 릴리스 기준으로 유지한다.

### `docs/troubleshooting/`

실제로 발생한 문제 중 원인과 재사용 가능한 해결 방법이 확인된 문제를
기록한다. 발생하지 않은 예상 오류나 검증되지 않은 추측은 작성하지 않는다.
문서는 원인과 해결 책임에 따라 `data/`, `backend/`, `frontend/`,
`integration/`에서 관리하며 실제 기록이 생길 때만 디렉터리를 생성한다.

### 영역별 기준 문서

아키텍처, API, 데이터, 운영 등의 문서는 현재 시스템의 계약과 사용 방법을
설명한다. 미래 설계안은 `docs/development/develop_plan/`에 두고, 구현과
검증이 끝난 뒤 기준 문서에 반영한다.

### 문서 위치 결정 순서

1. 아직 구현하지 않은 범위와 완료 기준이면 `develop_plan/<owner>/`를
   선택한다.
2. 실제 구현 내용과 검증 결과이면 `development_notes/<owner>/`를 선택한다.
3. 실제 발생했고 해결된 문제이면 `troubleshooting/<owner>/`를 선택한다.
4. 현재 시스템이 따라야 하는 계약이면 담당 영역 폴더가 아니라 `docs/data/`,
   `docs/api/`, `docs/architecture/`, `docs/operations/`의 기준 문서를
   갱신한다.
5. `<owner>`는 `data`, `backend`, `frontend`, `integration` 중에서 작업
   책임을 기준으로 고른다. 둘 이상의 영역이 공동 책임을 가지면
   `integration`을 사용한다.

문서를 작성한 사람이나 AI Agent의 역할이 아니라 변경 대상과 책임 경계를
기준으로 위치를 선택한다. 예를 들어 데이터 담당자가 API 계약을 수정했다면
`data/` 개발 기록만으로 대체하지 않고 `docs/api/`도 갱신한다.

## 4. 변경 유형별 갱신 기준

### 새로운 기능

- `CHANGELOG.md`의 `[Unreleased]`를 갱신한다.
- 개발 기록에 목적, 주요 변경 파일과 검증 결과를 기록한다.
- 기능이 바꾸는 API, 데이터, 아키텍처 또는 운영 문서를 갱신한다.

### 주요 버그 수정

- 사용자 동작, 데이터 정확성, 보안 또는 운영에 영향을 주면 변경 이력에
  기록한다.
- 해결에 시간이 들었고 재발 가능성이 있으며 원인이 확인되었다면 관련
  troubleshooting 문서를 작성한다.
- 오탈자, 코드 포맷 또는 동작에 영향 없는 내부 정리는 일반적으로 기록하지
  않는다.

### 데이터 Schema 변경

- 데이터 기준 문서와 실제 Schema 파일을 함께 수정한다.
- 필수값, `null`, 빈 배열, enum, 날짜 형식과 하위 호환성 영향을 명시한다.
- API, Fixture, Seed 또는 DB가 영향을 받으면 함께 갱신한다.
- 의미 있는 계약 변경은 변경 이력과 개발 기록에 남긴다.

### API 변경

- 엔드포인트, 요청·응답, 오류와 예시 문서를 실제 구현과 맞춘다.
- 호환성이 깨지는 변경과 소비자에게 필요한 조치를 명시한다.
- 변경 이력에 기록하고, 주요 설계 판단이 있으면 개발 기록에 남긴다.

### DB 변경

- 모델, Schema, ERD와 마이그레이션 중 프로젝트에서 사용하는 기준 자료를
  일관되게 수정한다.
- 적용 및 롤백 방법과 실제 검증 결과를 기록한다.
- 데이터 손실 가능성이 있는 작업은 위험과 보호 조치를 명시한다.

### 환경변수 또는 실행 방법 변경

- `.env.example`에는 변수명과 안전한 예시만 기록한다.
- 설정·실행 문서와 필요하면 루트 `README.md`를 갱신한다.
- 인증키, 실제 비밀번호, 개인정보는 코드와 문서에 기록하지 않는다.

### 라이브러리 또는 의존성 변경

- 라이브러리를 추가·제거·갱신하면 담당 애플리케이션의 manifest와 lockfile을
  같은 작업에서 갱신한다.
- Frontend는 `package.json`과 선택한 단일 lockfile, Backend는 합의한 Python
  manifest와 lockfile 또는 `requirements.txt` 계열을 사용한다.
- 로컬에만 설치하고 의존성 파일 갱신을 누락하지 않는다.
- 실제 설치·테스트한 고정 의존성과 문서의 실행 방법이 일치하는지 확인한다.
- 패키지 관리 방식이나 실행 환경 경계를 바꾸는 작업은 영향받는 담당자와
  통합·배포 담당이 함께 검토한다.

### 배포 및 운영 변경

- 컨테이너 또는 배포 아키텍처와 운영 절차를 함께 갱신한다.
- 실행 순서, 의존 서비스, 데이터 보존과 복구 영향을 명시한다.
- 팀 또는 사용자에게 의미 있는 변경은 변경 이력에 기록한다.

담당 영역의 일반 기능 Forest는 컨테이너 파일 작성을 기본 범위로 간주하지
않는다. Dockerfile, Compose와 전체 컨테이너 검증은 관련 결과가 병합된 뒤
별도의 Integration·Deploy Forest에서 수행한다.

## 5. 개발 계획 관리

Forest 개발 계획은 다음 상태 중 하나를 사용한다.

- `draft`: 검토 전 초안
- `approved`: 범위와 완료 기준이 합의됨
- `in-progress`: 하나 이상의 Slice를 구현 중
- `completed`: Forest 전체 완료 기준과 검증을 충족함
- `superseded`: 다른 계획으로 대체됨

`completed`로 변경할 때는 대응하는 Forest 개발 기록과 커밋 또는 PR을
연결한다.
`draft`와 `approved` 계획에는 개발 기록을 요구하지 않는다. `in-progress`로
변경할 때 같은 담당 영역에 대응하는 개발 기록을 생성한다.
`superseded`로 변경할 때는 대체 문서를 연결하고 이유를 남긴다. 완료된 계획은
개발 기록의 대용으로 다시 작성하지 않는다.

## 6. 개발 기록 작성 기준

Forest 단위로 문서를 작성하고 다음 내용을 기록한다.

- 작업 일자
- 작업 영역
- 관련 Issue, 브랜치 또는 Forest 계획
- 개발 목적
- Forest 범위와 Slice 진행 현황
- 구현 내용과 주요 변경 파일
- 설계 결정과 이유
- 실행한 검증과 결과
- 남은 작업 또는 알려진 제약

새 Forest 개발 기록을 추가하면
`docs/development/development_notes/README.md`,
`docs/development/develop_plan/README.md`와 `docs/index.md`의 색인을 함께
갱신한다.

실행하지 않은 테스트를 통과했다고 쓰지 않는다. 실패한 검증은 결과와 후속
조치를 숨기지 않고 기록한다.

## 7. Troubleshooting 작성 기준

다음 조건 중 하나 이상을 만족하고 원인이 확인된 경우 작성한다.

- 해결에 상당한 시간이 소요됨
- 다른 개발 환경에서도 반복될 가능성이 있음
- 원인이 직관적이지 않음
- 재사용 가능한 해결 또는 예방 방법이 있음

기록에는 증상, 발생 환경, 실제 원인, 해결 방법, 확인 방법과 예방 방법을
포함한다. 해결되지 않은 문제는 확인된 사실과 시도한 방법을 구분해 개발
계획이나 Issue에 기록한다.

## 8. 문서 작성 규칙

- 파일명은 특별한 이유가 없으면 소문자 `snake_case`를 사용한다.
- 문서 제목과 링크는 역할을 명확하게 표현한다.
- 같은 규칙을 여러 문서에 복제하지 않고 기준 문서로 연결한다.
- 문서는 현재 저장소 경로와 `cheongnyeon-alimi` 명칭을 사용한다.
- 코드, 필드와 명령은 백틱으로 표시한다.
- 날짜가 필요한 기록은 `YYYY-MM-DD` 형식을 사용한다.
- 문서 내 상대 링크를 사용해 저장소 이동과 GitHub 탐색을 지원한다.
- 예정, 검토 중, 확정, 구현 완료 상태를 명시적으로 구분한다.
- 새 문서는 실제 내용이 있을 때 생성하며 빈 문서와 빈 디렉터리를 남기지
  않는다.

## 9. AI Agent 작업 규칙

AI Agent는 작업 전에 다음을 수행한다.

1. 현재 브랜치와 작업 트리 상태를 확인한다.
2. `docs/index.md`, 이 정책, 관련 거버넌스 문서와 Forest 개발 계획을
   확인한다.
3. 변경이 계획, 구현 결과, 문제 해결 또는 현재 계약 중 어디에 해당하는지
   판단하고 담당 영역을 선택한다.
4. 기존 사용자 변경을 식별하고 보존한다.
5. 변경 범위, 완료 기준과 필요한 검증을 정한다.

작업 후에는 다음을 수행한다.

1. 실제 변경과 관련된 문서만 갱신한다.
2. 의미 있는 변경을 `[Unreleased]`와 개발 기록에 반영한다.
3. API, Schema, DB, 환경변수 또는 운영 변경의 기준 문서를 갱신한다.
4. 실행한 검증과 결과만 기록한다.
5. 링크, 비밀정보, 임시 파일과 빈 디렉터리를 확인한다.
6. 변경 내용을 간단히 리뷰하고 커밋 메시지를 제안한다.
7. 사용자의 명시적 요청 없이 커밋하거나 원격에 푸시하지 않는다.
8. 계획 문서와 실제 저장소 상태가 다르면 임의로 구조를 바꾸지 않고 차이를
   알린다.

## 10. 작업 완료 검토

- 계획과 구현 결과가 서로 다른 문서에 올바르게 기록되었는가?
- 변경 유형에 필요한 기준 문서를 모두 확인했는가?
- 문서가 실제 코드와 실행 결과를 정확히 반영하는가?
- 미확정 설계를 현재 동작처럼 표현하지 않았는가?
- 문서 링크와 경로가 유효한가?
- 비밀키, 개인정보 또는 비공개 데이터가 없는가?
- 임시 산출물, 테스트용 파일과 빈 디렉터리가 남아 있지 않은가?

문서 변경을 완료하기 전에 다음 검증을 실행한다.

```powershell
python scripts/validate_docs.py
```

검사 항목과 실패 처리 기준은
[문서 품질 검증](../development/documentation_validation.md)을 따른다.

이 정책을 변경할 때는 `docs/index.md`의 빠른 안내와 충돌하지 않는지 함께
확인한다.
