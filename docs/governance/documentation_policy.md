# 문서화 정책

## 목적

문서는 현재 코드, 데이터와 실행 방법을 이해하고 재현하는 데 필요한 정보를
제공한다. 작업 과정 자체를 모두 보존하기보다, 구현이 끝난 결과를 현재 계약과
운영 절차에 반영하고 오래된 계획이 사용자·심사자를 혼란스럽게 하지 않도록 한다.

## 권위 순서

문서와 실제 동작이 충돌하면 다음 순서로 사실을 확인한다.

1. 실행 코드, Migration, Compose와 배포 Workflow
2. 자동화된 계약·회귀 테스트와 실제 실행 결과
3. 아키텍처·API·데이터·운영 기준 문서
4. 제품 설명과 문제 해결 기록

차이를 확인하면 같은 변경에서 문서를 갱신한다. 구현하지 않았거나 실행하지 않은
내용을 현재 기능이나 통과 결과로 기록하지 않는다.

## 디렉터리별 책임

| 위치 | 책임 |
| --- | --- |
| `README.md` | 프로젝트 목적, 핵심 기능, 한 줄 실행과 필수 제한사항 |
| `docs/product/` | 현재 기능의 사용자 흐름, 작동 원리와 한계 |
| `docs/architecture/` | 현재 구성요소·DB·컨테이너 책임과 채택된 ADR |
| `docs/api/` | 현재 HTTP endpoint, 인증, 요청·응답과 오류 계약 |
| `docs/data/` | Source, Schema, 정규화, 품질, 공개 범위와 생명주기 |
| `docs/operations/` | 설치, 수집, 배포, 상태 확인과 복구 절차 |
| `docs/troubleshooting/` | 실제 발생하고 원인이 확인된 재사용 가능한 해결 기록 |
| `docs/development/` | 현재 기여자가 사용하는 로컬 설정·테스트·문서 검증 안내 |
| `docs/governance/` | 브랜치, 커밋, 리뷰, 역할과 문서 관리 규칙 |
| `docs/contest/` | 현재 제출 후보의 최종 체크리스트와 증거 안내 |
| `CHANGELOG.md` | 사용자·운영자에게 의미 있는 완료 변경 요약 |

예정 작업, 논의와 세부 수행 순서는 GitHub Issue·Pull Request에서 관리한다.
완료된 주차별 계획, 작업 Slice와 반복적인 구현 일지는 공개 제출 문서에
유지하지 않는다. 장기적으로 필요한 설계 판단은 ADR이나 현재 기준 문서에
흡수한다.

## 변경 유형별 갱신

### 사용자 기능

- `CHANGELOG.md`의 `[Unreleased]`에 의미 있는 결과를 요약한다.
- `docs/product/`의 흐름·한계와 관련 API 계약을 갱신한다.
- 데이터 판정이나 운영 방법이 바뀌면 해당 기준 문서를 함께 갱신한다.

### API·DB·Schema

- endpoint, 요청·응답, 오류와 호환성 영향을 실제 구현과 맞춘다.
- Migration, 모델, Schema, Fixture와 API 소비 테스트를 함께 대조한다.
- `null`, 빈 배열, enum, 날짜 형식과 rollback·데이터 보존 영향을 명시한다.

### 데이터 Source·정규화

- 공식 Source, 인증 필요 여부, 호출 경계와 재배포 범위를 기록한다.
- 추정하지 않는 값, invalid·partial 판정과 lifecycle 영향을 명시한다.
- 공개 dataset version별 고정 수치는 manifest 근거와 확인일을 함께 적는다.

### Docker·배포·환경변수

- 실제 Compose 서비스, 네트워크, Volume, 시작 순서와 health check를 갱신한다.
- `.env.example` 계열에는 변수명과 안전한 placeholder만 기록한다.
- 데이터 삭제 가능성이 있는 명령은 대상 확인과 보존 영향을 함께 설명한다.

### 문제 해결

`docs/troubleshooting/`에는 다음 조건을 만족하는 문제만 기록한다.

- 실제로 재현됐다.
- 원인이 확인됐다.
- 해결·예방 방법이 다른 환경에서도 재사용 가능하다.

기록에는 증상, 환경, 원인, 해결, 확인 방법과 현재 상태를 포함한다. 당시의
정책 수나 version이 현재 기준과 다르면 역사적 incident임을 명시하고 현재
권위 문서로 연결한다.

## 비밀정보와 공개 범위

다음을 문서, 화면 캡처, 로그 예시와 commit에 남기지 않는다.

- 실제 API key, PIN, access token과 private key
- 실제 DB 비밀번호와 credential이 포함된 URL
- 개인 연락처·식별정보와 공개가 허용되지 않은 Raw payload
- 개인 PC 절대경로, 계정명과 임시 파일 경로

명령 예시는 안전한 placeholder를 사용한다. hash는 비밀 원문을 복원하지 못하는
공개 artifact·identity 무결성 값일 때만 기록한다.

## 작성 규칙

- 파일명은 특별한 이유가 없으면 소문자 `snake_case`를 사용한다.
- 같은 계약을 여러 문서에 복제하지 않고 권위 문서로 연결한다.
- 코드, 필드, 명령과 경로는 백틱으로 표시한다.
- 날짜는 `YYYY-MM-DD`, 시간 판단은 필요한 경우 KST·UTC를 명시한다.
- 저장소 안 링크는 상대 경로를 사용한다.
- 현재 동작, 역사적 incident와 미확정 사항을 명확히 구분한다.
- 빈 문서·빈 디렉터리와 실행되지 않은 테스트 결과를 남기지 않는다.

## 작업 전 확인

1. 현재 브랜치·SHA와 working tree를 확인한다.
2. `docs/index.md`와 변경 영역의 기준 문서를 읽는다.
3. 기존 사용자 변경과 비밀정보 경계를 확인한다.
4. 코드·테스트·Compose·Migration에서 현재 사실을 검증한다.

## 작업 후 확인

1. 실제 변경과 관련된 기준 문서만 갱신한다.
2. 오래된 계획 표현, 깨진 링크와 중복 설명을 제거한다.
3. 실행한 검증과 결과만 기록한다.
4. 비밀정보, 임시 파일과 개인 경로가 없는지 확인한다.
5. 아래 문서 검증을 실행한다.

```powershell
python scripts/validate_docs.py
```

검사 세부사항은 [문서 품질 검증](../development/documentation_validation.md)을
따른다. 사용자의 명시적 요청 없이 commit, push, merge하거나 외부 Release를
변경하지 않는다.
