# 4주차 - 사용자·관리자 핵심 기능과 Release 2 기반

## 계획 정보

- 상태: draft
- 계획일: `2026-08-07`
- 대상 Release: `v0.5.0`
- 실행 주차: 4주차
- 공통 시작점: `2b33ed7` (`v0.1.0`)
- 주 담당: Data, Backend, Frontend
- 통합 담당: Team Leader
- 후속 역할: 보고서 담당·사용성 리뷰어·QA는 5주차 기능 구현·통합 종료 뒤
  Integration 07 A2부터 수행
- 권위 범위: 4주차 실행 순서, 담당자별 작업과 W4-G0~G4

이 문서는 Backend 04·05, Frontend 03·05, Data 03과 Integration 05·06·07의
Forest 계획을 대신하지 않는다. 각 담당자는 Forest 계획의 Slice와 완료 기준을
따르고, 이 문서에서는 한 주 안의 의존 순서와 공동 Gate만 조정한다.

## 목표

사용자·관리자 기능의 계약을 얇게 고정하고 실제 PostgreSQL → FastAPI →
React 흐름으로 연결한다. 4주차는 `v0.5.0` tag를 만드는 주차가 아니라
Data·Backend·Frontend 구현과 Team Leader midpoint를 끝내는 주차다.

보고서 대조, 독립 사용성 리뷰와 QA 수행은 4주차 완료 조건에서 제외한다.
이 역할들은 5주차 기능 연결과 담당자 자체 회귀가 끝난 뒤 수행하되,
`v0.5.0` 최종 Gate와 tag보다 먼저 완료해야 한다.

## 시작 조건

- Release 1이 `main` 커밋 `2b33ed7`, tag `v0.1.0`으로 발행됨
- `develop`과 `origin/develop`이 `2b33ed7`로 fast-forward됨
- Release 1 publication 문서가 실제 Git 상태와 일치함
- 기존 Backend 04·05, Frontend 03과 CollectionRun 계약 확인
- 각 담당자가 최신 `develop`에서 Forest 단위 브랜치를 사용함
- Integration 05 W4-G0 승인 전 기능 구현을 시작하지 않음

- 최소 CollectionRun DB 계약과 Runtime Raw 재처리
- 관리자 인증·권한, 추천, 사용자 로컬 기능과 품질 운영은 미구현

### 기존 계획

- Backend 04: 관리자 인증·권한 기준선, 상태 `draft`
- Backend 05: 실행 이력·상세·수동 실행 API, 상태 `draft`
- Frontend 03: 관리자 실행 이력·수동 실행 UI, 상태 `draft`
- Integration 05·06, Frontend 05, Data 03, Integration 07: 상태 `draft`

기존 Frontend 03에는 서명 토큰 방식이 승인될 때 필요한 최소 로그인·세션
획득 UI가 명시되지 않았다. W4-G0에서 토큰 발급 방식을 승인하면 Frontend 03
범위와 소비 계약에 로그인·토큰 보관·로그아웃을 추가한다. 다른 인증 방식을
선택하면 해당 방식에 맞춰 계획을 갱신한다.

### Frontend

### Team Leader - Integration

- Release 1 golden 검색·상세 회귀와 비밀정보 경계 확인
- 결함을 4주차 blocker 또는 5주차 구현·수정으로 분류

## 범위 밖

- 4주차 보고서 담당의 독립 근거 대조
- 4주차 사용성 리뷰어의 시나리오 수행
- 4주차 QA의 요구사항 추적표·탐색·전체 회귀 수행
- 일반 사용자 계정·서버 동기화·외부 알림
- ML·LLM·벡터 추천과 행동 학습
- Scheduler·분산 worker·WebSocket
- 데이터 수정·승인 관리 화면과 복잡한 대시보드
- Production Docker·Nginx·CI와 `v0.5.0` tag

지원 역할의 수행을 4주차에서 제외해도 Data·Backend·Frontend는 자기 영역의
단위·통합·Browser 검증을 생략할 수 없다. 독립 검증은 5주차 기능 연결 종료
뒤 Integration 07 A2에서 별도로 수행한다.

## 실행 원칙

1. W4-G0 승인 전 인증·저장·추천 DTO를 임의로 구현하지 않는다.
2. 관리자 축은 Backend 04 → Backend 05 → Frontend 03 순서를 지킨다.
3. W4-G0 뒤 Recommendation, Frontend 05와 Data 03은 병렬로 진행한다.
4. Backend는 관리자 Critical Path를 우선하고 추천은 기존 검색 primitive를
   재사용한다.
5. Frontend localStorage 기능은 일반 사용자 계정이나 서버 API를 요구하지
   않는다.
6. 날짜 미상·상시 정책에 임의 D-Day나 알림을 생성하지 않는다.
7. 수동 수집은 Scheduler·worker 도입 없이 W4-G0에서 승인한 최소 경계를 따른다.
8. 실행하지 않은 테스트와 독립 리뷰를 성공으로 기록하지 않는다.
9. API·DB·Schema가 바뀌면 기준 문서와 소비자 검토를 같은 Forest에서 갱신한다.

## 선행 관계와 Critical Path

### Critical Path A - 관리자

```text
W4-T0 Release 1·공통 SHA 확인
  → W4-G0 계약 승인
  → W4-B1 관리자 인증·권한
  → W4-B2 실행 이력 목록·상세
  → W4-B3 수동 실행·stale
  → W4-F1 관리자 인증 상태·세션 UI
  → W4-F2 관리자 실행 UI
  → W4-I1 관리자 actual E2E
```

### Critical Path B - 사용자

```text
W4-G0 계약 승인
  ├→ W4-B4 추천 API ───────→ W4-F3 추천 UI ─┐
  └→ W4-F4 로컬 사용자 기능 ────────────────┤
                                             → W4-I2 사용자 actual E2E
```

### Data 병렬 경로

```text
W4-G0 품질 계약
  → W4-D1 반복 실행 fixture
  → W4-D2 수정·중복 감지
  → W4-D3 실패 격리·품질 통계
  → W4-D4 관리자 DTO 소비 검토
  → W4-I1 관리자 actual E2E
```

Backend 05는 Backend 04를 기다리고 Frontend 03 actual 연결은 Backend 05를
기다린다. Frontend는 기다리는 동안 승인된 Mock·상태 UI와 Frontend 05를
진행할 수 있다.

## 단계별 실행과 Gate

### Phase 0 - Release 기준선과 계약 승인

#### 담당자별 작업

- `W4-T0` Team Leader: `main`, `develop`, `origin/*`, `v0.1.0`이
  `2b33ed7`을 가리키는지 확인하고 publication 문서를 마감한다.
- `W4-D0` Data: importer·upsert·CollectionRun과 품질 집계의 현재 동작·필드
  inventory를 작성한다.
- `W4-B0` Backend: 인증 부재, 관리자 endpoint 후보, 추천 service·repository
  재사용 지점과 OpenAPI 초안을 작성한다.
- `W4-F0` Frontend: 관리자 route·API client, 검색·상세·상태 관리와
  localStorage 사용 여부를 조사하고 TypeScript 소비 초안을 작성한다.
- `W4-I0` Team Leader: 세 초안을 Integration 05 결정표에 대조한다.

#### Gate W4-G0 - 계약 승인

- 일반 사용자 계정 제외와 localStorage 저장 경계가 확정됨
- 관리자 credential·토큰 수명·역할과 `401`·`403`이 확정됨
- Frontend의 로그인·토큰 보관·로그아웃 책임이 확정됨
- 추천 점수·이유·제외·미확정 조건과 자격 비확정 의미가 확정됨
- D-Day·내부 알림·`.ics`의 KST·날짜 미상 규칙이 확정됨
- 수동 실행 `202`·run ID·중복·stale와 품질 오류 노출이 확정됨
- Data·Backend·Frontend가 각 소비 초안을 검토함

모두 충족하면 Team Leader가 `W4-G0_APPROVED`를 기록한다. 미확정 사항이
구현을 막으면 담당·선택지·재개 조건을 기록하고 구현을 시작하지 않는다.

#### Backend

- `W4-B1`: Backend 04 관리자 인증·공통 dependency·`401`·`403`·OpenAPI 구현
- `W4-B2`: Backend 05 실행 이력 목록·상세·pagination·필터·오류 DTO 구현
- `W4-B3`: 수동 실행 `202`, run ID, Source별 중복 방지와 stale 판정 구현

#### Frontend

- `W4-F1`: W4-G0 승인 관리자 로그인·세션 획득·보관·로그아웃·보호 route

#### Gate W4-G1 - 기반 준비

- 각 담당의 승인 계약 소비 테스트가 존재함
- Backend 04 인증 우회·비밀정보 노출 테스트가 통과함

- 계약 변경이 필요하면 W4-G0 결정과 기준 문서를 먼저 갱신함

### Phase 2 - 기능별 세로 연결

#### 관리자 경로

- `W4-B5`: Backend 04·05 PostgreSQL·권한·transaction 통합 테스트
- `W4-F6`: Backend actual API로 관리자 인증·이력·수동 실행 연결
- `W4-D5`: 실제 또는 승인 snapshot 반복 실행과 품질 통계 확인

#### 사용자 경로

- `W4-B6`: 추천 실제 snapshot 관련도·이유·미확정·성능 회귀
- `W4-F7`: 추천 actual API와 localStorage·D-Day·알림·`.ics` 연결
- `W4-F8`: API 오류 토스트·재시도와 긴 지역 목록 Browser 회귀

#### Gate W4-G2 - 영역별 준비

- Data 단위·통합 테스트와 품질 통계가 통과함
- Backend 관리자·추천 API 단위·PostgreSQL 테스트가 통과함
- Frontend unit·lint·build와 Mock Browser 흐름이 통과함
- 미실행 또는 실패 검증이 명시되고 actual 통합을 막는 blocker가 분류됨

### Phase 3 - 실제 PostgreSQL 통합

- `W4-I1`: 관리자 로그인 → 실행 이력 → 수동 실행 → run 상태·품질 통계 E2E
- `W4-I2`: 조건 → 추천 → 이유 → 즐겨찾기 → D-Day·알림·`.ics` E2E
- `W4-I3`: Release 1 golden 검색·상세, loading·empty·error·partial 회귀
- `W4-D6`: 통합 중 발견한 품질·수정·중복 집계 문제 수정
- `W4-B7`: 권한·동시 실행·추천 의미·transaction 문제 수정
- `W4-F9`: 인증 상태·추천 이유·로컬 저장·날짜·오류 UI 문제 수정

#### Gate W4-G3 - 실제 연결

- 두 E2E가 실제 PostgreSQL·FastAPI·React에서 실행됨
- `401`·`403`, 중복 실행, stale, 날짜 미상과 localStorage 손상이 검증됨
- Release 1 검색 계약과 golden 결과에 차단 회귀가 없음
- Raw·credential·stack trace가 API·UI·로그·Git에 노출되지 않음

### Phase 4 - 담당자 회귀와 midpoint

- `W4-D7`: Data 전체 회귀와 실제 품질 통계 결과 정리
- `W4-B8`: Backend 전체 PostgreSQL·권한·추천·관리자 회귀 정리
- `W4-F10`: Frontend 전체 unit·lint·build·Browser 결과 정리
- `W4-I4`: 계약·구현·테스트·문서 일치와 blocker 분류

#### Gate W4-G4 - midpoint 판정

Team Leader는 담당자 자체 검증과 실제 두 E2E를 기준으로 다음 중 하나를
기록한다.

- `W4-G4_MIDPOINT_PASS`: 4주차 기능 연결 완료, 5주차 구현 보완·독립 검증 가능
- `W4-G4_CONDITIONAL`: 비차단 미완성의 담당·완료 조건이 명확함
- `W4-G4_BLOCKED`: 실제 연결 또는 필수 계약이 실패해 5주차 검증 착수 불가

보고서·사용성 리뷰·QA가 아직 수행되지 않았다는 사실은 이 Gate에서 숨기지
않는다. W4-G4는 Release 2 최종 Gate가 아니며 `v0.5.0` tag 근거로 사용할 수
없다.

## 인계사항 발생 조건

다음 실제 차단이 발생할 때만 `docs/index.md` 공동 인계 보드에 등록한다.

- 관리자 인증 방식이 Backend 04 또는 Frontend 03 구현을 막음
- CollectionRun 상태·동시 실행 계약이 Data·Backend에서 다르게 해석됨
- 추천 DTO·이유·미확정 조건의 Backend·Frontend 소비가 충돌함
- 품질 통계가 Raw·credential·내부 예외를 노출해야만 구현 가능함
- Schema·Migration 변경 없이는 반복 수집·수정 감지를 구현할 수 없음
- 실제 E2E가 다른 담당 Forest 변경 없이는 진행되지 않음

미래 계획 자체나 5주차 독립 검증 예정은 활성 인계사항으로 등록하지 않는다.
