# 4주차 - 사용자·관리자 핵심 기능과 Release 2 기반

## 계획 정보

- 상태: draft
- 계획일: `2026-08-07`
- 대상 Release: `v0.5.0`
- 실행 주차: 4주차
- 공통 시작점: `2b33ed7` (`v0.1.0`)
- 주 담당: Data, Backend, Frontend
- 통합 담당: Team Leader
- 지원 역할: 보고서 담당, 사용성 리뷰어, QA
- 권위 범위: 4주차 실행 순서, 병렬 작업과 W4-G0~G4

## 목표

사용자·관리자 기능의 범위를 얇게 고정하고 DB·API·UI를 실제 흐름으로
연결한다. 4주차는 `v0.5.0` tag를 만드는 주차가 아니라 기능 연결과 5주차
리뷰·안정화를 위한 midpoint를 만드는 주차다.

## 시작 조건

- Release 1이 `main` 커밋 `2b33ed7`, tag `v0.1.0`으로 발행됨
- `develop`과 `origin/develop`이 `2b33ed7`로 fast-forward됨
- Release 1 publication 문서가 실제 Git 상태와 일치함
- 기존 Backend 04·05와 Frontend 03 계획·CollectionRun 계약 확인
- Integration 05 W4-G0 승인 전 기능 구현을 시작하지 않음

## 범위와 우선순위

### P0 - 4주차 필수

- 사용자·관리자·추천·수집·품질 계약 Gate
- 관리자 인증 → 실행 이력·수동 실행 API → 관리자 UI
- 조건 기반 결정적 추천 → 이유·미확정 조건 → 추천 UI
- 반복 수집의 unchanged·updated·duplicate·failed 통계
- 사용자 조건·즐겨찾기·D-Day·내부 알림·`.ics`의 브라우저 로컬 기능
- Release 1 이관 API 오류 토스트와 긴 지역 목록 축약
- 실제 PostgreSQL 기반 두 핵심 E2E와 기존 검색 회귀

### 범위 밖 또는 5주차 이후

- 일반 사용자 계정·서버 동기화·외부 알림
- ML·LLM·벡터 추천과 행동 학습
- Scheduler·분산 worker·WebSocket
- 데이터 수정·승인 관리 화면과 복잡한 대시보드
- Production Docker·Nginx·CI와 `v0.5.0` tag

## Forest와 의존 관계

```text
Integration 05 W4-G0 계약 승인
  ├→ Backend 04 → Backend 05 → Frontend 03 ──────────┐
  ├→ Integration 06 추천 Backend·Frontend ───────────┤
  ├→ Frontend 05 로컬 사용자 기능 ───────────────────┤
  └→ Data 03 반복 수집·품질 운영 ────────────────────┤
                                            → Integration 07 midpoint
                                            → 5주차 리뷰·QA·Release 2 Gate
```

관리자 축만 순차 실행한다. W4-G0 뒤 추천, Frontend 로컬 기능과 Data 품질
작업은 병렬로 진행한다. Backend는 관리자 Critical Path를 우선하고 추천은
기존 검색 primitive를 재사용해 새 검색 엔진을 만들지 않는다.

## 단계별 일정과 Gate

### 1일차 - W4-G0 계약 동결

- Release 1 publication 문서 마감
- 사용자 저장·개인정보·알림 경계 결정
- 관리자 credential·토큰·역할과 `401`·`403` 결정
- 추천 점수·이유·미확정 조건과 자격 비확정 의미 결정
- 수동 실행 `202`·run ID·중복·stale·품질 오류 노출 결정
- Data·Backend·Frontend 소비 초안 공동 검토

완료 신호: `W4-G0_APPROVED`

### 2일차 - W4-G1 기반 준비

- Backend: Admin Access Control 구현·보안 테스트
- Backend: 추천 DTO와 기존 판정 primitive 연결 준비
- Frontend: 승인 DTO Mock, localStorage contract와 화면 상태 준비
- Data: 반복 실행·수정·중복·실패 fixture와 기대 통계 고정

완료 신호: 역할별 구현 시작을 막는 계약 미확정 0건

### 3일차 - W4-G2 기능별 세로 연결

- 관리자 실행 이력·상세·수동 실행 API와 관리자 UI 연결
- 추천 API·이유·미확정 조건과 추천 UI 연결
- 조건·즐겨찾기·D-Day·내부 알림·`.ics` 연결
- unchanged·updated·duplicate·failed 품질 통계 생성

완료 신호: 각 Forest의 Mock·단위·통합 테스트 통과 또는 blocker 명시

### 4일차 - W4-G3 실제 통합

```text
사용자 조건 → 추천 → 이유 → 즐겨찾기 → D-Day·알림·캘린더
관리자 로그인 → 실행 이력 → 수동 실행 → run 상태·품질 통계
```

- 실제 PostgreSQL·FastAPI·React에서 두 흐름 검증
- loading·empty·error·partial, `401`·`403`, 중복 실행 확인
- Release 1 golden 검색·상세 회귀 확인

완료 신호: 실제 E2E 증거와 재현 가능한 결함 목록

### 5일차 - W4-G4 midpoint와 5주차 인계

- Data·Backend·Frontend 관련 전체 회귀
- 모바일·키보드·기본 접근성과 민감정보 비노출 확인
- 미완성·결함·위험을 blocker 또는 5주차 수정으로 분류
- 보고서 근거와 5주차 사용성·QA 시나리오 준비

완료 신호: `W4-G4_MIDPOINT_PASS` 또는 blocker·재개 조건 기록

## 역할별 완료 책임

| 역할 | 4주차 책임 |
| --- | --- |
| Data | 반복 수집, 수정·중복·실패 격리와 품질 통계 |
| Backend | 관리자 인증·실행 API, 결정적 추천 API와 자동 테스트 |
| Frontend | 관리자 UI, 추천 UI, 로컬 사용자 기능과 오류·축약 UX |
| Team Leader | W4-G0 계약, 의존성·중간 E2E와 midpoint 판정 |
| 보고서 | 결정·화면·테스트와 미실행 검증 근거 누적 |
| 사용성 리뷰어 | 5주차 독립 시나리오·질문과 기대 결과 준비 |
| QA | 요구사항 추적표, 실제·경계·실패 데이터와 지원 환경 준비 |

## 4주차 완료 기준

- W4-G0 계약과 담당별 소비 초안 승인
- 관리자 인증 → 실행 API → UI가 실제 DB로 연결됨
- 사용자 조건 → 추천·이유 → 즐겨찾기·D-Day·알림·`.ics`가 연결됨
- 반복 수집 결과가 unchanged·updated·duplicate·failed로 구분됨
- loading·empty·error·partial과 주요 권한 오류가 존재함
- 실제 두 E2E와 Release 1 검색 회귀 결과가 기록됨
- 5주차 리뷰·QA 시나리오, blocker와 재검증 조건이 준비됨
- 실행한 검증만 개발 기록에 기록하고 문서 검증이 통과함

## 검증 기준

각 Forest의 명령을 우선하며 주 후반 통합에서는 최소 다음을 실행한다.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_*.py" -v
$env:TEST_DATABASE_URL = '<dedicated-postgresql-test-url>'
.\.venv\Scripts\python.exe -B -m pytest backend/tests -q
Set-Location frontend
npm run test
npm run lint
npm run build
npm run test:e2e
Set-Location ..
python scripts/validate_docs.py
git diff --check
```

PostgreSQL 통합 환경이나 Browser가 준비되지 않으면 성공으로 처리하지 않고
해당 Gate의 blocker와 재실행 조건을 기록한다.
