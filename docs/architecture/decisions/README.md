# 아키텍처 결정 기록

이 디렉터리는 시스템의 구조, 책임 경계와 운영 방식에 장기적인 영향을 주는
결정을 Architecture Decision Record(ADR)로 관리한다.

## 현재 ADR

- [ADR 0001 정책 검색 데이터 기반](0001-policy-search-data-foundation.md):
  `proposed`, Source 중립 검색 필드와 행정구역·정책 관계·projection

## ADR이 필요한 변경

- 데이터 파이프라인 계층 또는 공통 계약 변경
- 서비스와 저장소의 책임 경계 변경
- 새로운 런타임 서비스나 컨테이너 도입
- DB, 메시지 큐, Scheduler 등 핵심 기술 선택
- 인증, 권한 또는 운영 데이터 보존 구조 변경
- 기존 선택을 대체하거나 되돌리기 어려운 결정

작은 구현 세부사항, 쉽게 되돌릴 수 있는 로컬 리팩터링과 단순 의존성
업데이트는 일반적으로 ADR 대상이 아니다.

## 파일 이름

```text
NNNN-short-title.md
```

- `NNNN`은 `0001`부터 증가하는 네 자리 번호다.
- 제목은 영어 소문자와 하이픈을 사용한다.
- 번호는 재사용하지 않는다.

예:

```text
0001-separate-collector-module.md
0002-introduce-collector-worker.md
```

예시는 이름 형식 설명이며 현재 채택된 결정이나 생성 예정 파일을 뜻하지
않는다.

## 상태

- `proposed`: 검토 중
- `accepted`: 채택되어 적용 대상
- `superseded`: 새 ADR로 대체됨
- `deprecated`: 더 이상 권장하거나 적용하지 않음

`superseded`는 대체 ADR을 연결한다. 채택된 ADR의 결론을 조용히 다시 쓰지
않고, 변경이 필요하면 새 ADR을 작성한다.

## ADR 형식

```markdown
# ADR NNNN: 결정 제목

- 상태: proposed
- 작성일: YYYY-MM-DD
- 결정자:
- 관련 Issue/PR:

## 맥락
## 결정
## 고려한 대안
## 결과
## 검증 방법
## 후속 작업
```

### 맥락

결정이 필요한 문제, 제약과 현재 상태를 설명한다.

### 결정

채택할 선택과 적용 범위를 명확히 기록한다.

### 고려한 대안

검토한 선택지와 채택하지 않은 이유를 기록한다.

### 결과

장점, 비용, 위험, 호환성과 운영 영향을 기록한다.

### 검증 방법

결정이 의도대로 작동하는지 확인할 방법을 기록한다.

### 후속 작업

필요한 코드, 문서, Migration 또는 운영 변경을 연결한다.

## 작성 절차

1. 계획 또는 Issue에서 결정이 필요한 문제를 식별한다.
2. `proposed` ADR을 작성하고 영향받는 담당자와 검토한다.
3. 합의 후 `accepted`로 변경한다.
4. 코드와 기준 문서를 같은 작업 흐름에서 반영한다.
5. 실제 구현이 결정과 다른 경우 임의로 ADR을 수정하지 않고 차이를 알린다.

ADR을 추가하면 [아키텍처 문서 안내](../README.md)와 필요한 기준 문서에서
연결한다.
