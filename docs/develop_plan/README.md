# 개발 계획 관리

`docs/develop_plan/`은 아직 완료하지 않은 작업의 범위, 의존성, 수행 순서와
완료 기준을 합의하는 공간이다. 실제 구현 결과는
[`development_notes.md`](../development/development_notes.md)에 기록한다.

## 계획과 결과의 경계

- 개발 계획은 무엇을, 왜, 어떤 순서와 기준으로 할지 설명한다.
- 개발 기록은 실제로 무엇을 변경하고 어떻게 검증했는지 설명한다.
- 변경 이력은 사용자와 팀에 의미 있는 결과만 요약한다.
- troubleshooting 문서는 실제 발생하고 해결된 문제를 설명한다.

계획 문서에 구현 예정 사항을 완료된 사실처럼 표현하지 않는다. 구현 과정에서
계획이 달라지면 상태와 변경 이유를 갱신한다.

## 상태

각 계획은 문서 상단에 다음 상태 중 하나를 표시한다.

| 상태 | 의미 |
| --- | --- |
| `draft` | 검토 전 초안 |
| `approved` | 범위와 완료 기준이 합의됨 |
| `in-progress` | 구현 중 |
| `completed` | 완료 기준과 검증을 충족함 |
| `superseded` | 다른 계획으로 대체됨 |

`completed` 상태에는 관련 개발 기록과 커밋 또는 PR을 연결한다.
`superseded` 상태에는 대체 계획과 변경 이유를 기록한다.

## 계획 문서 필수 항목

새 계획은 다음 항목을 포함한다.

```markdown
# 계획 제목

- 상태:
- 담당 영역:
- 관련 Issue:
- 대상 브랜치:

## 목적
## 범위
## 범위 밖
## 선행 조건
## 설계 결정
## 변경 예정 파일
## 구현 순서
## 테스트 계획
## 완료 기준
## 위험 요소
## 문서 갱신 대상
```

Issue, 브랜치 또는 변경 예정 파일이 확정되지 않았다면 `미정`으로 표시하고
결정 전까지 임의로 사실처럼 채우지 않는다.

## 운영 규칙

1. 구현 전에 목적, 범위, 범위 밖과 완료 기준을 검토한다.
2. 하나의 계획은 독립적으로 검토 가능한 작업 단위를 다룬다.
3. 다른 작업에 의존하면 선행 계획과 필요한 상태를 명시한다.
4. 구현 중 설계가 바뀌면 결정과 이유를 계획에 반영한다.
5. 완료할 때 실행한 테스트와 결과는 개발 기록에 남긴다.
6. 계획 완료 후에도 문서를 삭제하지 않고 추적 정보를 유지한다.
7. 같은 내용을 계획과 개발 기록에 장문으로 중복하지 않고 서로 연결한다.
8. 비밀키, 비밀번호, 개인정보와 비공개 원문을 기록하지 않는다.
9. 실제 내용이 없는 계획 파일과 빈 디렉터리를 만들지 않는다.

## 파일 구성

계획은 로드맵이나 기간보다 작업 단위가 명확하게 드러나도록 구성한다.
주차별 계획이 필요한 경우 `week-01/`처럼 두 자리 숫자를 사용한다. 여러
계획에 공통으로 영향을 주는 미확정 결정은 별도의 의사결정 문서로 분리할 수
있다.

새 경로나 문서를 추가하면 [`docs/index.md`](../index.md) 또는 상위 계획의
목차를 함께 갱신한다.
